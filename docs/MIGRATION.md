# 무료 운영 전환 설계

## 목표와 기준

- Firebase Spark(Cloud Billing 미연결) + Vercel Hobby만 사용한다. Pro 체험, Blaze, 유료 도메인, Marketplace, Cloud Functions, App Hosting은 도입하지 않는다.
- 무료 한도 소진 시 중단을 수용한다. 무료 무제한·무중단을 약속하지 않는다.
- Firebase 프로젝트와 Vercel 계정 생성은 사용자 확인으로 완료했다. Firebase 프로젝트 ID는 board-game-kraken(894297269744)이며 Spark를 콘솔에서 확인했다. DBG 웹 앱 등록, CLI 인증, dbg-kraken 무료 사이트 확보와 서울 기본 DB·Rules 배포까지 완료했다. 실제 웹사이트 공개는 Google 로그인·Vercel API 설정 후 진행한다. 사이트 표시 이름은 DBG, 기존 RDS 사용자는 이전하지 않고 새로 시작한다.
- 기존 Java 소스는 비교·회귀 검증 기준으로 유지한다. 새 구현은 TypeScript로 화면/API/게임 규칙을 분리한다.
- 디자인은 기존 Spring Boot 템플릿·스크린샷에 맞춘다. 회색 배경·파란 버튼·표 형태 로비·방 생성 모달·왼쪽 참여자/채팅/컨트롤·회색 카드·노란 턴 강조를 유지한다. 모바일은 원본처럼 하단 참여자/채팅/컨트롤 탭과 바텀 시트를 사용한다. 게임 동작은 변경하지 않는다.

게스트 로그인은 기존 기본 경로에서 비활성화되어 있다. 로컬 데모 인증으로 대체하되 운영에서는 Google만 허용한다. 기존 취약점(참여하지 않은 방 조작, XSS, 중복 시작)은 동등성 대상이 아니다. 진행 중 퇴장 시 기존 게임의 카드/역할은 유지한다(기존 동작); 빠진 사람 차례에는 기존과 동일하게 재입장 등 없이는 진행이 막힐 수 있다. 개선은 별도 요구로 다룬다.

## 구조

- client: React + Vite, 화면/폼, Firebase Auth, Firestore 읽기 구독. 운영 쓰기는 모두 API.
- api/command.ts: Vercel HTTP 진입점. ID 토큰 검증, 허용 Origin, 입력 검증.
- server: 서비스/저장소. 운영 Firestore 트랜잭션, 로컬 메모리 저장소.
- shared/game.ts: 네트워크·DB·화면에 의존하지 않는 게임 규칙. 서버에서만 카드 종류/역할 결정.
- Firebase Hosting은 정적 화면과 무료 web.app 주소만 제공한다. Vercel에는 API만 배포한다.

공개 방 상태, 플레이어 본인 손패/역할, 서버 전용 카드 위치/비밀번호 해시를 서로 다른 문서로 분리한다. 공개 정보에 비밀 데이터가 한 번이라도 내려가지 않도록 한다. Admin SDK는 Rules를 우회하므로 API에서도 참가·방장·턴을 검사한다.

## DB 최소화

- users/{uid}: username, roomCode, 마지막 채팅 시각. 이메일·프로필 사진·로그인 이력은 복제하지 않는다.
- names/{닉네임의 SHA-256 해시}: uid만 저장(중복 방지).
- rooms/{code}: 제목, 정원, 방장, 참가자, 공개 게임 상태, 현재 채팅의 제한된 최근 목록. 별도 채팅 히스토리 컬렉션은 만들지 않는다.
- secrets/{code}: 비밀번호 해시와 진행 중 게임 원본. 클라이언트 접근 금지.
- rooms/{code}/players/{uid}: 본인 역할·손패 구성만 저장. 게임 종료 시 삭제.
- 결과와 참여 방 참조는 10초 화면 표시용으로 짧게 유지하고 정리한다. 전적·통계·턴 로그·접속 로그·분석 데이터를 저장하지 않는다.
- 최근 채팅 40개, 각 300자만 유지한다. 종료/빈 방 삭제 시 함께 제거한다. 재접속 후 오래된 채팅 전부를 복원하는 기능은 기존에도 없다.
- 대기·진행 방은 마지막 실제 활동 24시간 이후 정리 대상으로 삼는다. 진행 중 접속 화면이 열려 있다는 이유만으로 주기적 DB 쓰기는 하지 않는다.
- Spark 유료 TTL/스케줄러를 사용하지 않는다. API 요청 시 소량 정리 + 수동 cleanup 명령. 모든 접속이 끊기면 만료 데이터가 다음 요청까지 남을 수 있으나 실행 중 청구는 없다.
- collection list는 제한하고, 로비를 떠나면 구독 해제한다. 채팅 때 로비 전체 문서를 재전송하지 않도록 로비 요약은 별도 최소 문서로 운용할 수 있으나 우선 불필요한 복제보다 단순성을 선택한다.

## 타이머와 동시성

서버리스 응답 이후 setTimeout/메모리 상태에 의존하지 않는다. 라운드 전환 시각을 저장하고 클라이언트가 기한에 advance 요청을 보낸다. 서버 시각과 트랜잭션으로 한 번만 전환한다. 전원 탭 중단 중에는 저장 상태가 다음 요청 시 진행된다(상시 스케줄러 없음). 3초/10초 화면 동작은 재진입 시 남은 시간 기준이다.

카드 요청에는 라운드·상태 버전을 포함하여 중복 요청이 다음 턴에 재적용되지 않도록 한다. 트랜잭션 재시도에 대비해 알림 같은 외부 부작용은 넣지 않는다.

## 검증과 출시 차단 조건

1. 규칙 테스트: 4/5/6인 덱·역할, 모든 승패, 턴, 재배분, 중복 선택, 권한.
2. API 테스트: 닉네임 유일성, 비밀번호, 한 명 한 방, 준비/강퇴/위임, 동시 요청, 데이터 삭제.
3. 브라우저: 별도 사용자 4명으로 로비·채팅·준비·시작·카드·재진입, 모바일 레이아웃.
4. Firebase Emulator: Rules로 비밀·다른 사람 손패 접근 차단 및 운영 저장소 트랜잭션 확인.
5. 실제 Spark/Hobby: Google 로그인, Origin, 구독 지연·사용량 검증. 운영 프로젝트 미연결 상태에서는 완료로 표시하지 않는다.

미통과 항목이 있으면 기존 Java 구현을 대체한 출시 완료라고 표시하지 않는다.

## 추가 기능: 한번 더하기

사용자 승인으로 종료 후 10초 재참가 접수를 추가했다. 1명부터 새 공개 대기방을 만들며 기존 최소 4인 시작·준비 규칙은 유지한다. 신청자 UID만 종료된 방에 잠시 기록하고 새 방 생성·참여 참조 이동·기존 결과 정리를 한 트랜잭션으로 처리한다. 세부 동작과 검증 범위는 [REMATCH.md](REMATCH.md)를 따른다.
